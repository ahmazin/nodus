# Releasing Nodus

Nodus publishes its `@nodus-dev/*` packages with [changesets](https://github.com/changesets/changesets).
A release is three steps: contributors add a **changeset** to their PR describing the change and its
bump; the version step turns accumulated changesets into version bumps and CHANGELOG entries; a
maintainer runs the publish. This document is the mechanics; the guarantees a version bump makes to
consumers are in [`docs/stability.md`](./docs/stability.md).

> Publishing to npm is a **human-run** step. Nothing in CI publishes automatically.

## The flow

### 1. Add a changeset (every PR that changes a published package)

```bash
pnpm changeset
```

This prompts for the affected packages, the bump type (`patch` / `minor` — see the 0.x rules in
[`docs/stability.md`](./docs/stability.md#semver-under-0x)), and a summary. It writes a small Markdown
file under `.changeset/`. Commit it with your change. A PR that touches a published package's public
behavior without a changeset is incomplete.

### 2. Version the packages (maintainer, at release time)

```bash
pnpm version-packages     # = changeset version
```

This consumes every pending `.changeset/*` file and, in one commit:

- bumps each affected package's `version`,
- writes a per-package `CHANGELOG.md` entry from the changeset summaries,
- bumps dependents whose internal dependency ranges moved (see `updateInternalDependencies` below).

Review the resulting diff — the version bumps and generated CHANGELOGs are the release's public
record — then commit it.

### 3. Publish (maintainer)

```bash
pnpm docs:api             # regenerate the typedoc API reference the site serves at /api/
pnpm release              # = pnpm verify:all && changeset publish
```

`pnpm release` gates on `verify:all` (typecheck + test + verify:render + verify:dist), so a red tree
cannot publish. `changeset publish` then publishes every package whose version is ahead of npm and
creates the git tags. The API reference under `apps/site/public/api/` is generated output
(gitignored) — regenerate it before any site deploy.

## Configuration (`.changeset/config.json`)

| Setting | Value | Effect |
|---|---|---|
| `access` | `public` | Scoped `@nodus-dev/*` packages publish publicly (scoped packages default to restricted otherwise). |
| `updateInternalDependencies` | `patch` | When package A is released, dependents on A get at least a patch bump so their pinned range moves with it. |
| `baseBranch` | `main` | The branch changeset status compares against. |
| `commit` | `false` | Changesets never auto-commit; you stage the changeset and the version bump yourself. |

**Private packages are skipped automatically.** Anything with `"private": true` in its
`package.json` (`@nodus-dev/site`, the browser example, and any package not yet meant for npm) is never
versioned or published by changesets. Publishable packages carry no `private` field and rely on their
`publishConfig` for the published shape.

## Canonical-byte changes

Canonical `*.nodus.json` bytes are a versioned contract: a change to canonical output is
semver-breaking (a minor bump under 0.x). See
[`docs/stability.md`](./docs/stability.md#canonical-serialization-bytes-are-a-breaking-contract) for
why. Concretely, when a PR alters canonical serialization output:

1. Regenerate the checked-in **golden canonical fixtures** so the byte-equality test reflects the new
   output (rather than editing the assertion to match).
2. Include the regenerated fixtures **and** a `minor` changeset in the **same PR**, so the byte change
   and its version signal ship together.

The `nodus fmt --check` gate and `canonical.test.ts` catch drift within a release; the fixtures +
changeset rule is what makes the drift a deliberate, versioned event across releases.

## CHANGELOGs

Every published package gets a `CHANGELOG.md` generated by `changeset version` from the changeset
summaries — so consumers can assess upgrade risk per package. Do not hand-edit generated CHANGELOG
entries; write the changeset instead, and let the version step render it.
