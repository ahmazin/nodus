# Nodus API Contract Audit — Production Adoptability & Extensibility

**Date:** 2026-07-24
**Scope:** the public API surface of all 18 `@nodus/*` packages, judged as an external library consumer or extension author would — what *contracts* (guarantees, lifecycles, typed surfaces, policies) are missing, partial, undocumented, or inconsistent versus a production-grade library.
**Method:** 57-agent workflow — 11 parallel audit lanes (surface governance, Editor façade, extensibility axes, error semantics, lifecycle, serialization compat, events/reactivity, packaging, docs/DX, React binding, peer benchmark vs tldraw/CodeMirror 6/React Flow/Excalidraw/ProseMirror/Lexical) → dedup/prioritize → one adversarial verifier per finding, prompted to *refute* the gap by locating the contract in code, docs, tests, or CI.
**Result:** 104 raw findings → 45 merged → **45 survived verification (37 confirmed, 8 adjusted, 0 refuted)**.

---

## Verdict: solid engine, unfinished contract

The architecture is genuinely production-shaped — one mutation channel, registry-driven extension axes, deterministic serialization, a headless-identical renderer. What's missing is almost never *mechanism*; it's the **promises around the mechanism**: what an adopter may rely on across versions, what an extension author is guaranteed at each lifecycle point, what happens on failure, and what the published packages actually resolve to on npm. Severity distribution: **1 P0 · 22 P1 · 22 P2 · 0 P3** — the P3s were merged away or dropped by the synthesis pass, meaning nearly everything that survived is contract-load-bearing.

## The seven themes

### 1. Dependency topology is the publish blocker (P0)
Every extension package (presets, layouts, plugins, importers, stencils, persistence, cli, mcp — 16 in all) hard-depends on `@nodus/core` via `dependencies: { "@nodus/core": "workspace:*" }`, which `pnpm pack` rewrites to an **exact pin** (`"0.1.0"`). The first post-publish core patch release therefore strands every published plugin: consumers hit npm `ERESOLVE` or silently get **two nested core instances** — two signal engines, two registries — and because `Editor` has private fields (`packages/core/src/editor/index.ts:283-286`) the class is *nominal*, so `editor.use(plugin)` fails to typecheck across copies. Fix: `peerDependencies` with `workspace:^` ranges everywhere, plus a verify-dist assertion that rejects exact-pinned `@nodus/*` ranges in packed manifests.

### 2. The React adoption path fails on framework defaults
The first 30 minutes of a React adopter's evaluation currently hits, in order: **StrictMode** (on by default in every template) silently kills the *recommended* `useNodusEditor` hook — after the dev remount cycle the ref-held editor is disposed and never rewired, giving a dead canvas with zero errors, while the hook's own JSDoc claims StrictMode safety; **Next.js/SSR** throws on the server (`useValue`'s `useSyncExternalStore` has no server snapshot, bare `useLayoutEffect`, no `'use client'` banner in dist); the canvas host attaches **document-global keyboard/clipboard handlers** that alter typing in the embedding app; and mounting initiates **undisclosed third-party network requests**. Each one alone reads as "the library is broken" to an evaluator.

### 3. The git-native moat lacks its own guarantees
The product's identity is "diagrams you can code-review," but: loading a document with a **newer `schemaVersion`** silently strips what the older library doesn't understand and restamps the file — a destructive rewrite of exactly the file format whose value proposition is trustworthy round-trips; the canonical byte format has **no checked-in golden fixtures** with byte-equality tests and no policy that byte-affecting changes are semver-breaking; and **counter-based id generation** lets two independent writers (two git branches, two editors) mint the same id for different content — the foundational gap under any future merge/collab story.

### 4. Extension authors get a surface, not a contract
A record whose type has no registered util becomes **silently invisible** (tldraw refuses loudly instead); plugin installation is neither idempotent nor reversible, and `EngineHost` exposes essentially the whole application façade rather than a stable boundary; custom-type migrations are positional array steps with no stable ids; there is **no pre-commit interception** (the tldraw `sideEffects.registerBefore*` / ProseMirror `filterTransaction` equivalent) and **no engine-level command registry** (the CodeMirror/Lexical precedent) — hosts, palette, and menus each rebind actions ad hoc.

### 5. Failure semantics are ad hoc
No shared coded error taxonomy across packages (and bare `Error(string)` is fragile against the dual-package `instanceof` hazard); façade methods disagree — the same class of failure throws in one method, returns null in another, `console.warn`s in a third; the event bus is not a closed discriminated union (`error`/`theme` arms undeclared); signal `effect()` errors have undefined semantics (no `onReactionError`-style hook).

### 6. The public surface is ungoverned
`export * from './model.js'` drags the entire model module into the public API unaudited; there is no api-extractor-style report or release-tag discipline (`@public`/`@internal`), no machine check that types reachable from public signatures are themselves exported, no stated semver/stability/deprecation policy, and no per-package CHANGELOG. Under Hyrum's Law, everything currently observable is already a de-facto contract — the surface should be deliberate before first publish, when narrowing it is still free.

### 7. Docs promise what the code doesn't do
The hook JSDoc claims StrictMode safety that isn't real; documented samples and CLI invocations don't all run as shown; the `.get()`-subscribes-vs-`.peek()` rule — the codebase's own #1 footgun per CLAUDE.md — is not stated on the members themselves; the advertised headless path (CreateCanvas injection, font loading, type registration) is undocumented; there is no generated API reference.

## P0 — publish blockers

### F1 · packaging — missing
**Contract:** Extension packages (presets, layouts, plugins, importers, stencils, persistence) declare @nodus/core as a peerDependency with a compatible range, and workspace links publish as ranges (workspace:^), so exactly one core instance resolves per app and a core patch never strands or duplicates the engine.
*(merged from 3 independent lane findings)*
**Evidence:** All extension packages hard-depend on core via workspace:* with no peerDependencies (packages/plugin-freehand/package.json, preset-draw:17, layout-dagre:23, preset-infra:23-25, persistence:17, import-infra:17, text-to-diagram:17, from-mermaid:18, stencils:18). Verified via pnpm pack: workspace:* rewrites to exact pins ("@nodus/core": "0.1.0" in preset-infra; @nodus/react even peer-pins core and stencils to 0.1.0). Editor has private fields (packages/core/src/editor/index.ts:283-286), making the class nominal across module instances. .changeset/config.json:9 forces full-lockstep republish.
**Impact:** The moment two release waves exist, consumers get either a hard npm ERESOLVE failure or a silently nested second @nodus/core: editor.use(plugin) fails typecheck (nominal Editor from the other copy) and the runtime ships two signal engines/registries. Every core patch release strands every published plugin until it re-releases.
**Recommendation:** Move @nodus/core to peerDependencies with workspace:^ (devDependencies workspace:* for the inner loop) in every extension package; add a verify-dist assertion rejecting exact-pinned @nodus/* ranges in packed manifests; document the single-instance requirement in EXTENDING.md.
**Verification (confirmed):** Checked every packages/*/package.json via grep. The gap is real as stated: all extension packages hard-depend on core in "dependencies" with "@nodus/core": "workspace:*" — preset-infra/package.json:23-24, preset-draw:17, preset-diagrams:18, plugin-freehand:18, persistence:17, stencils:18, import-infra:17, from-mermaid:18, text-to-diagram:17, layout-dagre:23-24, layout-tree:18, layout-force:18, layout-elk:18, icons-cloud:42-43, cli:18-19, mcp:18-19. Zero occurrences of "workspace:^" anywhere in packages/ (grep -rln returned nothing). The only package with peerDependencies is @nodus/react (react/package.json:23-25), and it peer-declares @nodus/core and @nodus/stencils as "workspace:*", which pnpm publish rewrites to the exact pin 0.1.0 — matching the cited pnpm-pack evidence. Editor nominal-typing claim holds: packages/core/src/editor/index.ts:283-286 has private fields (zCounter, loadedTypeVersions, disposers), so instanceof/assignability breaks across duplicate core instances. .changeset/config.json:9 is "updateInternalDependencies": "patch" with "fixed": [] — the finding's phrasing "forces full-lockstep republish" is slightly imprecise (it is not changesets fixed-mode lockstep; rather patch-bump-of-dependents which, combined with exact pins, has the same effective result), but this does not change the status. No mention of peer-dependency strategy anywhere in README.md, packages/*/README.md, apps/site/src/pages/docs/, or PRE-PUBLICATION-AUDIT.md (grep empty). Contract is missing as claimed.


## P1 — major adoption / extension friction

### F2 · react-binding / lifecycle — inconsistent
**Contract:** The recommended React lifecycle hook survives React 18/19 StrictMode's dev-only mount-unmount-remount cycle: after the simulated remount the returned editor is fully functional.
*(merged from 2 independent lane findings)*
**Evidence:** packages/react/src/use-nodus-editor.ts:48-52 builds the Editor into a ref during render; :60-64 registers cleanup () => editor.dispose(). StrictMode reruns the effect with no re-render, so the same now-disposed editor is reused; dispose() permanently drains the disposer list including the sole store-to-sceneIndex/history/eventBus wiring (packages/core/src/editor/index.ts:2669-2672, 313-321) with no re-wiring path. The comment at :57-59 claims StrictMode safety. No test covers it; the repo's own example avoids the hook (examples/browser/src/main.tsx:683 useMemo under StrictMode at :1677).
**Impact:** Every adopter following the hook's own JSDoc in a default-config Next.js/Vite/CRA dev app gets a silently dead canvas after mount: mutations stop reaching the scene index, history, and event bus — no paint, no hit-test, no undo, dead plugins — reading as engine flakiness during the adoption-evaluation phase, with zero errors thrown.
**Recommendation:** Add an Editor.disposed flag and make the effect setup re-run the factory when the ref-held editor is disposed (or create in the effect); add a StrictMode double-mount browser-verify test; fix the misleading comment.
**Verification (confirmed):** Checked all cited locations plus barrel, docs, examples, tests. (1) packages/react/src/use-nodus-editor.ts:48-52 builds the Editor into a useRef during render and returns ref.current.editor; :60-64 registers useEffect cleanup () => editor.dispose() keyed on deps. Under StrictMode's dev mount→unmount→remount, React re-runs only the effect (cleanup then setup) with no re-render, so ref.current is never rebuilt and the same disposed editor is returned and reused. (2) packages/core/src/editor/index.ts:2669-2672 dispose() runs every disposer and clears the list; :313-321 shows the single store.listen wiring (sceneIndex.applyChanges, reconcileFlowIndex, history.record, events.emit) is registered exactly once in the constructor — after dispose there is no re-wiring path, so store changes stop reaching the scene index, history, and event bus; :324-331 also tears down flow sources. Idempotency (comment at use-nodus-editor.ts:57-59 claiming StrictMode safety) only prevents double-free, not the dead-editor state. (3) The hook is the exported public contract (packages/react/src/index.tsx:14) and is the documented recommendation (apps/site/src/pages/docs/index.md:30-39 shows useNodusEditor + <Nodus>). (4) The repo's own example runs under StrictMode (examples/browser/src/main.tsx:1677) but uses useMemo(buildEditor, []) at :683, not the hook — consistent with the hook being unsafe there. (5) No test covers the remount cycle: packages/react/src/__tests__/ contains only canvas-registry, cloud-icon-picker, flow-controls, panels-logic tests; vitest runs in node env (no jsdom), and no StrictMode reference exists in any test or CI workflow. The evidence citations are all accurate; status 'inconsistent' is correct (comment/docs promise StrictMode safety the implementation does not deliver).

### F3 · react-binding / SSR — missing
**Contract:** The React binding renders safely under react-dom/server or enforces client-only usage: useSyncExternalStore has a server snapshot, no bare useLayoutEffect warnings, and published dist carries a 'use client' banner for RSC consumers.
*(merged from 2 independent lane findings)*
**Evidence:** packages/react/src/use-value.ts:15 passes no third getServerSnapshot argument — React 18 throws 'Missing getServerSnapshot' on any server render; <Nodus> is affected via <EditOverlay> (nodus-host.tsx:357, 367-368), as are Properties, Minimap, FlowControls, LayersPanel, CommandPalette. nodus-host.tsx:10,55 uses bare useLayoutEffect (SSR warning). tsup.config.ts has no banner and grep finds no 'use client' anywhere. **Impact:** In Next.js — the mainstream React path, both routers — importing <Nodus> or any panel throws on the server; App Router consumers first hit the cryptic 'useState only works in Client Components' error. Adopters must independently discover dynamic(..., { ssr: false }).
**Recommendation:** Pass getServerSnapshot (signals are safe to read server-side; core is DOM-free), add banner: { js: "'use client';" } to tsup, adopt useIsomorphicLayoutEffect, fix the README quickstart to useNodusEditor, add an SSR section and a node-environment barrel-import smoke test.
**Verification (confirmed):** Checked every cited location. packages/react/src/use-value.ts:15 calls useSyncExternalStore with only two args — no getServerSnapshot, so React 18 server render throws. packages/react/src/nodus-host.tsx:10,55 uses bare useLayoutEffect with no SSR-safe fallback, and <Nodus> unconditionally renders <EditOverlay> (~line 357) which uses useValue, making <Nodus> itself crash under react-dom/server. packages/react/tsup.config.ts has no banner option; grep across packages/*/src, tsup configs, package.json files, and apps/site/src finds zero occurrences of 'use client'. packages/react/README.md:21 instantiates new Editor() at module scope with no client-only caveat, and the README contains no ssr/server/next mention. apps/site docs' only 'server-side' hit (docs/index.md:74) refers to headless Skia PNG rendering, not React SSR. ### F4 · packaging / TypeScript resolution — partial
**Contract:** A dual ESM/CJS package resolves correct type declarations under every documented moduleResolution mode: the require export condition serves CJS-flavored declarations (.d.cts).
**Evidence:** Every publishConfig exports map is { types: ./dist/index.d.ts, import: ./dist/index.js, require: ./dist/index.cjs } with one shared ESM-flavored types condition (packages/core/package.json:37-43, react:46-52, identical in the other 16). tsup does emit dist/index.d.cts and files:['dist'] ships it, but no condition references it. scripts/verify-dist.mjs:292-293 only checks the file exists on disk; no consumer typecheck runs.
**Impact:** Every CJS TypeScript consumer under moduleResolution node16/nodenext gets TS1479 ('is an ECMAScript module and cannot be imported with require') on all 18 packages even though runtime require works — a hard adoption blocker for CJS codebases, invisible to the current verifier.
**Recommendation:** Restructure each exports entry as { import: { types: ./dist/index.d.ts, default: ./dist/index.js }, require: { types: ./dist/index.d.cts, default: ./dist/index.cjs } }; run @arethetypeswrong/cli (or a tsc node16 consumer typecheck of both flavors) against packed tarballs in verify-dist.
**Verification (confirmed):** Checked packages/core/package.json:13,33-45 (type:module; publishConfig exports = shared types:./dist/index.d.ts + require:./dist/index.cjs), packages/react/package.json:13,42-52 (identical), and grep across all 18 publishable packages: every one has require->index.cjs and none has a d.cts condition. packages/core/tsup.config.ts (format esm+cjs, dts:true) does emit index.d.cts and it ships, but it is orphaned — the only repo references to d.cts are scripts/verify-dist.mjs:292-293, which merely existsSync-check the file; lines 275-288 runtime-test CJS require but no consumer typecheck under node16/nodenext exists anywhere (grep for attw/arethetypeswrong/moduleResolution in scripts/ and .github/ is empty). Because every package is type:module, the shared index.d.ts is ESM-flavored, so a node16/nodenext CJS consumer gets ESM types with a CJS runtime file — the TS1479 'masquerading as ESM' mismatch. README.md:161 documents the dual ESM+CJS contract. Gap is real exactly as stated; 'partial' is the right status since ESM and bundler-mode consumers plus CJS runtime all work.

### F5 · serialization / forward compatibility — partial
**Contract:** A git-native format never destructively rewrites what it does not understand: documents with a newer schemaVersion are refused or preserved (never silently stripped and restamped older), and unknown top-level fields either round-trip or are reported when stripped.
*(merged from 2 independent lane findings)*
**Evidence:** restore() treats schemaVersion > SCHEMA_VERSION as a swallowable 'bad-schema-version' issue and does a best-effort current-schema load (packages/core/src/serialization/index.ts:307-318); normalizers rebuild records from fixed whitelists (:231-301) so any newer or third-party top-level field is dropped, and serializeRecords restamps SCHEMA_VERSION (:93-103). Empirically verified: a schemaVersion:2 snapshot with extension fields loads, the fields vanish, output is restamped v1. The SerializationIssue union has no 'unknown-field' code (:23). Contrast: the typeVersions axis correctly preserves forward data and max-merges on save (:373-382; editor/index.ts:1597-1607) — the two version axes have opposite forward-compat behavior, and the internal migrations spec promises preservation the schemaVersion axis does not deliver.
**Impact:** The moment SCHEMA_VERSION 2 ships, any teammate or CI on the older library that opens-and-saves (or runs nodus fmt on) a v2 file destructively downgrades it — new fields deleted, envelope restamped v1 — with no visible error. For a product whose moat is trustworthy file round-trips this is the forbidden failure mode, and it must be decided before v2 exists because the OLD binary is the one that misbehaves. Third-party top-level annotations also vanish on first fmt with no signal.
**Recommendation:** Decide the contract now: hard-fail restore() on newer schemaVersion (recommended for a git-native format) or preserve-unknown and re-emit the original version. Add an 'unknown-field' issue code; document whitelist semantics and props/meta as the sanctioned extension slots in schema.md; mirror the behavior in loadSnapshot and the CLI with a distinct 'file is newer than this tool' error.
**Verification (confirmed):** Checked packages/core/src/serialization/index.ts in full: restore() clamps any schemaVersion > SCHEMA_VERSION to a 'bad-schema-version' issue and proceeds with a best-effort current-schema load (:310-318); normalizeNode/normalizeEdge/normalizePage rebuild records from fixed field whitelists (:231-301) so unknown/newer top-level record fields are silently dropped; serializeRecords restamps SCHEMA_VERSION=1 unconditionally (:99); the SerializationIssue union (:23) has no 'unknown-field' code. The behavior is deliberate and locked in by test: packages/core/src/serialization/hardening.test.ts:111-121 asserts schemaVersion 999 "still best-effort loads". No caller refuses or even surfaces the issue: editor loadSnapshot (packages/core/src/editor/index.ts:1618-1620) calls restore() without onError, and all four CLI commands (packages/cli/src/commands/fmt.ts:23, diff.ts:11, render.ts:42, drift.ts:25) also call restore() without onError — so `nodus fmt` on a hypothetical v2 file would silently strip unrecognized fields and rewrite it as v1 (fmt's `dropped` counter tracks only whole dropped records, not stripped fields). Contrast confirmed: the typeVersions axis does preserve forward data (unmigrated keep-raw at serialization/index.ts:373-382) and max-merges on save (editor/index.ts:1597-1607, computeTypeVersions), so the two version axes genuinely have opposite forward-compat behavior. Docs (apps/site/src/pages/docs/schema.md, README.md:182, packages/core/README.md:82) describe schemaVersion as the migration axis but nowhere disclose the strip-and-restamp behavior. Nothing in barrels, tests, or .github/workflows/diagrams.yml implements refusal or preservation. Status 'partial' is correct as claimed.

### F6 · core / id generation — inconsistent
**Contract:** Id generation is instance-scoped and collision-resistant, so two independent writers (git branches, two editors) cannot mint the same id for different content — the prerequisite for git-mergeable documents.
**Evidence:** makeId derives ids from a module-global deterministic counter (packages/core/src/model.ts:230,239-247); seedIdCounter advances that process-global counter on every Store.load (model.ts:268-280; store/index.ts:256-258), so loading document B mutates id state for every other Editor in the JS context; restore() dedupes duplicate ids last-wins (serialization/index.ts:332-340); seedIdCounter is public API via the model.ts wildcard barrel export.
**Impact:** Directly breaks the moat scenario: two branches from one baseline seed the counter identically, each new node gets the identical id for different content; a git merge yields a duplicate id and restore() silently keeps only the last occurrence — one author's node is dropped. Multiple editors on one page also interleave ids through hidden shared state.
**Recommendation:** Make id generation per-editor and collision-resistant by default (nanoid-style random component, or per-editor counter plus random session prefix), keep the deterministic counter as an opt-in for golden-file tests, and stop exporting seedIdCounter from the barrel.
**Verification (confirmed):** Checked all cited code plus barrel, docs, and tests; the gap is real as stated. (1) packages/core/src/model.ts:230 declares `let idCounter = 0` as a module global; makeId (model.ts:244) mints ids from it deterministically (`autoIdSuffix(idCounter++)`, model.ts:239), while its doc comment at model.ts:243 claims a "stable, collision-resistant id" — collision-resistance holds only within one JS context. Two independent writers (two git branches, two processes) starting from the same document deterministically mint IDENTICAL ids for different content. (2) seedIdCounter (model.ts:275) is called from Store.load (packages/core/src/store/index.ts:258) and advances the process-global counter, so loading document B mutates id state for every Editor in the context — confirmed, and it only mitigates same-context reopen collisions, not cross-writer ones. (3) restore() dedupes duplicate ids last-wins with only an optional onError callback (packages/core/src/serialization/index.ts:338-340), meaning a git-merged file with colliding ids silently drops one side's record — data loss in exactly the flagship workflow. (4) Both makeId and seedIdCounter are public API: packages/core/src/index.ts:5 (`export * from './model.js'`) and dist/index.d.ts:2420. (5) The mergeability contract is advertised: apps/site/src/pages/docs/concepts.md:72-74 promises *.nodus.json gets "clean, line-by-line diffs, blame, review, and merge". (6) Tests (packages/core/src/model.identity.test.ts:30-73) cover only single-context reopen and counter recovery — no test covers two-writer/branch-merge collision. Refutation attempts failed: no random/instance-scoped id path exists, no CLI/CI duplicate-id merge gate found. Status "inconsistent" is correct (code comment + docs claim collision-resistance/mergeability the implementation cannot deliver across writers). Severity P1: silent data loss on merge of the advertised git-native workflow, though it requires concurrent branch edits and project memory notes distributed id creation was a known deferred decision.

### F7 · serialization / canonical format — missing
**Contract:** A published on-disk byte format is pinned by checked-in golden fixtures with byte-equality tests, and byte-affecting changes are declared semver-breaking.
**Evidence:** All six canonical tests are self-referential round-trips of the current implementation (packages/core/src/__tests__/canonical.test.ts:20-84); packages/cli/src/cli.test.ts:38-103 same pattern; no golden .nodus.json fixture or *.schema.json exists anywhere (find). The CI gate cannot catch it either: .github/workflows/diagrams.yml:10-13 triggers only on PRs touching *.nodus.json, so a core serialization change never runs fmt --check.
**Impact:** Any stableStringify/compareRecords/canonicalRecord refactor that alters bytes passes the entire suite, ships in a patch release, and then every adopter's committed diagrams fail nodus fmt --check CI on untouched files — fleet-wide breakage of the headline feature, undetectable before release.
**Recommendation:** Check in golden fixtures (unicode ids, typeVersions, pages, coerced values) with byte-equality assertions against toCanonicalString; document canonical bytes as a semver-major contract in schema.md; run fmt --check over committed diagrams whenever packages/core/src/serialization/** changes.
**Verification (confirmed):** Checked all cited evidence plus counter-search. packages/core/src/__tests__/canonical.test.ts:20-84: all six tests compare toCanonicalString output to itself after round-trip — self-referential as claimed, no pinned bytes. packages/cli/src/cli.test.ts:38-103: fixtures generated from the live Editor into a temp dir, same pattern (header comment at cli.test.ts:3-4 even says bytes 'come from @nodus/core'). find confirms no *.schema.json and no golden fixture; the only checked-in diagram (examples/infra/sample.nodus.json) is used only by the semantic drift gate (.github/workflows/drift-check.yml:35), never byte-compared. CI gap confirmed: diagrams.yml:10-13 triggers only on **/*.nodus.json paths, and drift-check.yml:12-17 excludes packages/core/**, so a core serialization change runs neither gate. No semver-breaking policy: apps/site/src/pages/docs/schema.md documents the format without any stability/breaking declaration; packages/core/package.json is 0.1.0. Minor caveat that does not change the status: packages/core/src/serialization/typeversions.test.ts:17,20 hard-codes two literal canonical byte strings and cli.test.ts:100 asserts a literal typeVersions substring — real inline byte pins, but they cover only the empty-document envelope/typeVersions map, not record-level bytes (key order, number normalization), so the contract is still effectively missing.

### F8 · editor facade / hydration — inconsistent
**Contract:** Constructing an editor with initial records is equivalent to loading a snapshot — one canonical hydration path running migrations, z-counter seeding, and active-page initialization — or the difference is explicitly documented.
**Evidence:** The constructor path is store.load + sceneIndex.rebuild + rebuildFlowIndex only (packages/core/src/editor/index.ts:333-337); loadSnapshot additionally runs restore() with migrations (:1620), seeds zCounter past the largest loaded z (:1631-1639), and sets the active page (:1628). EditorOptions.records carries no doc comment stating any of this (:139-148).
**Impact:** An adopter who persists snapshot.records and rehydrates via the constructor gets silently skipped type migrations (data corruption on the first schema evolution), new nodes painting UNDER loaded content (zCounter restarts at 0), and multi-page documents rendering all pages overlapped.
**Recommendation:** Delegate constructor hydration to the same path as loadSnapshot, or document EditorOptions.records as already-migrated raw single-implicit-page input and at least seed zCounter and the active page in the constructor.
